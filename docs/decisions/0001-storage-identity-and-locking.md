# 0001 — Native Git storage and publication fences

Use one bare Git object database per repository. Reserve `/git-store/repositories/<uuid>` for bare data and separate sibling directories for manifests and stable lock inodes. Sync also has a private staging and quarantine mount. PostgreSQL will own the catalog, visibility state, publication sequences, and jobs. Git refs alone grant no visibility. Phase 0 creates synthetic bare repositories and a database probe relation.

Use UUIDv4 for repositories, sources, requests, and transient attachments. Qualify UUIDv7 before use for jobs, notifications, or incidents. Use separate per-repository nonnegative BIGINT generation IDs and publication sequences, serialized as decimal strings on the wire. Allocate unique typed advisory lock keys. OIDs carry a repo scope, a format, and the full native digest. SHA-1 is 20 bytes and SHA-256 is 32 bytes. Qualify SHA-256 reads and fetch before advertising support.

Use a writer filesystem coordinator and matching session advisory lock, then the repository filesystem and advisory fences. Canonical writers acquire the sync-private storage admission lock before taking generation filesystem and advisory fences in ascending ID order. Readers share fences and recheck visibility in a fresh READ COMMITTED READ ONLY statement. Keep the filesystem fence until subprocesses have been reaped, including after DB loss. Writers take the repository filesystem fence exclusively for canonical installation, retirement, and maintenance. Install and flush objects, refs, and manifests before committing the PostgreSQL pointer and outbox. Treat the DB commit as the visibility boundary.

Protect three inactive generations plus all generations demoted within 24 hours as initial design defaults. Phase 0 measures basic flock and fsync behavior on the chosen local filesystem. Phase 1 defines the manifest encoding and qualifies the native reader. Phase 2 covers acquisition. Phase 3 defines the operator commands, publication recovery, and guarded maintenance.
